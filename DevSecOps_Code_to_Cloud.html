01 · The big idea

Why DevOps, and why add “Sec”?

Software used to be built by separate teams that rarely talked. DevOps joined them. DevSecOps makes security part of the same team and the same automation.

DEVELOPERSOPERATIONS 👩‍💻
📦😩

😬 The old way

  • Developers “throw code over the wall” to Ops
  • Big releases every 3–6 months, often over weekends
  • Manual servers, manual testing, lots of “works on my machine”
  • Security reviews only at the very end — slow, and usually too late
∞

🔁 DevOps

  • Dev + Ops = one team that owns the app end-to-end
  • Automate everything: build, test, infrastructure, deploy (CI/CD)
  • Small changes shipped many times a day
  • Measure, learn, repeat — a never-ending loop
🛡️🔍🔐📜

🛡 DevSecOps

  • Security is everyone's job, not a final gate
  • Automated security checks run inside every stage
  • Shift left: find problems early, when they're cheap to fix
  • Shield right: keep protecting the app while it runs
Remember this one line: DevOps makes you fast. DevSecOps makes you fast and safe — the security checks run automatically so they don't slow the team down.
02 · How we got here

Waterfall → Agile → DevOps

Each approach made software delivery faster. The biggest change DevOps brought: deployment went from a big, risky event to a routine, low-risk activity. Click through the three eras.

Deployment: then vs now

🗓️ Earlier — traditional IT

  • 📦
    Quarterly releasesLarge batches of changes deployed over weekends.
  • 🌙
    DowntimePlanned maintenance windows were common (“site down Saturday 11 PM – 6 AM”).
  • 💣
    RiskOne defect could impact the entire release.
  • 🐢
    RollbackOften manual, complex and time-consuming.

⚡ Now — modern DevOps & CI/CD

  • 🔁
    Frequent deploymentsSmaller changes released daily, or even many times a day.
  • 🟢
    Minimal downtimeRolling, blue-green and canary deployments keep the site up.
  • ✅
    Automated validationTesting, security scans and quality gates run before production.
  • ↩️
    Faster recoveryAutomated rollback, feature flags and continuous monitoring.

Try it: a canary release in production

Instead of switching all 30M users to the new version at once, ShopKart sends a small slice of traffic to it first (the “canary”). Tools like Argo Rollouts or Flagger watch error rate and latency, then automatically promote — or roll back.

The name comes from coal miners, who took canaries underground as an early warning of danger.

Who does what?

👩‍💻
Developer

Writes features and tests, fixes what the pipeline flags. In DevSecOps, also fixes security findings in their own code.

🧪
QA / SDET

Builds automated test suites (UI, API, performance) that run in the pipeline.

🏗️
DevOps / Platform engineer

Builds the shared CI/CD platform, templates and Kubernetes clusters that all teams use.

🚒
SRE (Site Reliability Eng.)

Keeps production reliable: SLOs, monitoring, on-call, incident response, capacity.

🛡️
AppSec / Cloud security engineer

Chooses and tunes the security tools, writes policies, triages findings, coaches developers.

📋
Release / Change manager

Governs risky changes and freeze windows (e.g. sale days) and keeps audit trails for compliance.
